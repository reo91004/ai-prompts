# Investigating An Unexpected Result

Simple code and proportionate validation leave room for deep scientific analysis. Use the following questions as relevant, not as a mandatory checklist for every run.

1. **What was observed?** Separate software failure, an inconclusive experiment, a supported positive or negative finding, and a reviewer's judgment. State the strongest result the evidence establishes.
2. **Could the result be wrong?** Check implementation, data processing, metric direction/definition, baseline fairness, and configuration where evidence makes them plausible causes.
3. **Under what conditions?** Examine uncertainty, noise, sample size, budgets, operating regimes, and method assumptions. Distinguish a local failure from a general limit.
4. **What could explain or improve it?** Rank plausible causes by evidence and impact. Follow the shared research principles on mechanism hypotheses and timely discriminating exploration. Propose concrete remedies and the smallest discriminating experiment or analysis for each promising cause. Broader analysis is warranted when causes remain ambiguous.
5. **What changes the conclusion?** Incorporate new evidence, preserve the original result, and report which explanations remain hypotheses. A useful next step may improve the method, narrow the valid regime, or establish a meaningful limit.

If Codex is pessimistic, ask it to identify the evidence behind the judgment, plausible alternative explanations, and a test or remedy that could change it. Do not request optimism or agreement. Reuse that exchange in the current review rather than adding an approval layer.

Do not cherry-pick seeds, metrics, subsets, or reruns to reverse a negative result. Label exploratory analysis and confirm new hypotheses on appropriate independent evidence when making a confirmatory claim. Continue while a relevant hypothesis, new evidence, and the authorized resource budget support progress; ask about scope or resources only when the next experiment actually needs a user decision.
